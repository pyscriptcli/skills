# Benchmark Comparison

## First: grill user

Ask this before research or doc writing. Ask all at once. Short.

1. What are we comparing?
2. Which options? Exact names.
3. Who reads this? Who decides?
4. What job must winner do?
5. What use case matters most?
6. What criteria do you want?
7. What matters most? Rank it.
8. Deal breakers? Budget? Must-have? Privacy? Region?
9. Facts only or recommendation too?
10. Wanted bottom line: one winner, winner by case, or no winner?
11. Wanted final action: buy, test, build, keep current, short list?
12. Sources, prices, notes to use?

Ask only missing important stuff after this.
If user says `just do it`, say assumptions. Then do it.

## Research

- Use current official sources for price, features, limits, integrations.
- Unknown = `Unknown`. Do not guess.
- Fact and opinion are not same thing.
- Same criteria for every option.
- Put risk in its own row.

## Document shape

```text
TITLE
Option A vs. Option B vs. Option C - month year

Goal Workflow
- What user needs done
- Input -> work -> output
- Needed integrations

Comparison Summary
| Criteria | Option A | Option B | Option C |
|---|---|---|---|
| [criterion] | [answer] | [answer] | [answer] |

Bottom Line
- Best overall. Why.
- Main weak spot.

Decision Rule
- If [situation], pick [option].

Recommended Architecture or Next Steps
- How winner fits workflow.
- Setup path. Owner. Biggest risk.
```

## Use good table rows

- core job fit
- quality
- workflow fit
- integrations / API / automation
- setup time
- cost now and later
- privacy / security
- support / reliability
- main risk

No junk rows. No feature pile.

## End hard

```text
Recommendation: [pick]
Why: [top 2 or 3 reasons]
Do not pick it if: [deal breaker]
Next step: [small test, purchase, pilot, or build]
```

## Voice

- Short. Plain. Direct.
- Tables do heavy work.
- No filler. No sales talk.
- Clear winner or clear decision rule.
- Do not hide uncertainty.
